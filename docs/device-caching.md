# Device caching

Nourishing stores account-specific screen data and saved photos in IndexedDB. A verified sign-in selects the account before cached responses can be read. On a later launch, the server document supplies an opaque binding for the current session. If it matches the last verified session saved on this device, the diary renders from IndexedDB while account validation runs in the background. A new or missing session binding cannot resume another account’s cache. The binding contains no credentials and is never accepted by an API as authentication; a rejected session locks and clears cached access. External PWA launches can omit Strict cookies on their initial document request. When that happens, a small same-origin request retrieves only the session binding before reading saved data. This request does not contact Appwrite or grant API access. Bootstrap and account validation share a 15-second deadline. Opening a saved screen uses that local response immediately. Responses older than 30 seconds refresh in the background; main views apply the result when no editor is open. The first visit also warms the main Discover and Foods reads, with at most two background requests at a time.

More → Account uses the same account-scoped cache for name, email, verification status, time zone and units. The authentication request itself stays network-only; credentials and provider fields are excluded. Returning to More keeps the current shell and search state. Account edits invalidate the display cache.

Diary and converted editor saves enter the account's IndexedDB outbox before the editor closes. Serializable requests retain their operation IDs across reloads and retries. The local view applies pending changes immediately. A single background worker verifies the account and restore generation, then sends changes in order. A lost reply retries the same request; acknowledgements update the local baseline, translate temporary record IDs, and remove the saved command in one transaction. Storage failures keep the editor open.

Queued writes mark cached responses stale and retain them for immediate rendering with pending changes. Other cloud-only operations still invalidate affected responses. Cache tickets include the account, session epoch and cache revision. A response from an older ticket cannot repopulate the cache or replace the screen after invalidation. A restored workspace generation clears response caches and holds old pending changes for review. More → Device storage provides retry, export and discard controls for this same outbox.

The response/photo cache holds up to 128 entries and 20 MiB, evicting least recently used entries. Individual JSON responses are limited to 2 MiB and photos to 8 MiB. The separate full offline diary snapshot and queued edits are preserved outside that LRU. The app refreshes the full snapshot after loading and after writes. Logout clears private data, with the existing Sync/Discard/Cancel choice when offline edits remain. Session expiry locks the snapshot and clears responses. Account changes cannot expose another account's cached data.

Public UI scripts, styles, icons and fonts use a release-versioned service-worker cache. The normal diary's startup dependency graph, styles and fonts are downloaded before an update becomes ready. Other public assets are cached when used. Offline navigation opens the same diary shell and uses the last verified, unlocked device account. Online session validation remains authoritative; expiry and account changes lock private access. API responses, photos, credentials and authentication pages never enter the shared public cache. Passwords and session cookies are not response-cache entries. Pending photo saves can retain the short-lived server review token needed to finish that save, inside the account's private outbox.

Discover supports single-finger left/right swipes between Dashboard, Charts, Report and Snapshots, without wrapping. Content follows the horizontal drag and slides into the adjacent tab when it is ready. A slow uncached response uses its normal loading view after a 400 ms transition bound. Reduced-motion preferences and unsupported browsers use direct navigation. Horizontal swipes can start over cards, charts, buttons and expandable headings. Taps still open those controls. Vertical scrolling, form inputs, sliders, horizontally scrolling areas and dialogs keep their own behavior. Gesture capture remains active within Discover during a native slide, so consecutive swipes do not need to wait for the animation to finish.

Validation evidence is recorded in PROGRESS.md. Desktop browser checks do not establish physical-device notification delivery or camera behavior.

The network-loaded update bootstrap checks for a waiting service worker on launch and when the app returns online or to the foreground. A small Update ready / Reload control activates the waiting release and reloads only the accepting window. Other windows retain unsaved forms and can reload separately. A worker capability check prevents offering activation for an older waiting release that lacks the handler. The bootstrap and its stylesheet are excluded from CacheStorage. This follows the [explicit update pattern](https://developer.chrome.com/docs/workbox/handling-service-worker-updates).
